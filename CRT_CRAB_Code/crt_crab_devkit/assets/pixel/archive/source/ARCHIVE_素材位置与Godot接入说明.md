# ARCHIVE 档案仓库 · 素材位置与 Godot 接入说明（v1.0）

## 1. 范围、技术基线

仓库：<https://github.com/Qisi3344/clawd-crt-tower>  
工程：`CRT_CRAB_Code/crt_crab_devkit/`。引擎 Godot 4.x；主游戏外壳为 3D CRT 塔，屏内横版冒险使用 320×240 单活动 `SubViewport`。  
目标地图 `data/levels/archive_01.json`：**1024×640**，当前是 **一张连续世界**，不要按旧房间拆多张传送图。  
目前 `scripts/world_backdrop.gd` 仍画重复矩形柜墙和线框 shelves 地标；`scripts/side_world.gd` 负责装配世界，`main.gd` 负责屏幕视口。素材包只处理 **ARCHIVE 视觉**，不修改其他五关、不改玩法。

### 真实关卡的三个垂直分区

| area ID | 中文区域 | JSON 的区域矩形（x,y,w,h） | 视觉任务 |
|---|---|---|---|
| `upper` | 上层检索桥 | `(0,0,1024,112)` | 轻、空、高：远处高柜顶、检索桥阴影、档案悬挂带、吊灯，避免遮住上层真实平台及梯子 |
| `main` | 重压归档大厅 | `(0,112,1024,176)` | 最强的档案仓库身份：高柜、抽屉、检索台、文件推车、编号柜区；真实压板和箱石永远清晰 |
| `lower` | 破损记录仓 | `(0,288,1024,352)` | 更暗、更破损：倾倒记录箱、裂屏检索终端、封存箱、纸带机、裸露电缆；不伪造能踩的破桥 |

> JSON 的 `rect` 是大分区包围盒，不等于该区全范围均可站立。具体地面、平台、梯子和机关以 `platforms`、`ladders` 等数据和实机画面为准。道具位置应基于真实可落脚平台确定，而非简单按照分区中心点摆放。

## 2. 两张背景图怎么用

### 2.1 远景 `ARCHIVE_far_source_远景.png`

- 背景层：参考 `z_index=-30`，全景柜体结构和远处桥架，用低对比度及柔和紫黑色显示。
- 只随镜头**缓慢**偏移（建议约 0.1–0.2 倍水平镜头运动作初始调试），不要让背景像主角一样快速跑动。
- 源图 **2172×724**、3:1；与世界 **1024×640**、活动屏 **320×240** 比例都不同，必须先在编辑器/离线制图里明确缩放及裁剪策略。不要仅凭宽度强行拉伸至 1024×640。
- 确认没有明显左右拼接缝之前**不要开循环重复**；如果边缘不连续，宁可仅使用一个可裁剪区段再补辅助柜墙。
- 远景层应在 320×240 下仍留下主角和互动元素的对比度。

### 2.2 中景 `ARCHIVE_mid_source_中景.png`

- 参考 `z_index=-20`，主要为玩家能辨认的背景建筑细节：抽屉柜墙、检索机、书架和文件箱。
- **这张图绘制了楼梯、检索桥和梯子，它们只是画面里的图形，没有游戏碰撞**；不要整体平铺成虚假的可走路径。最好选择截取不冲突的柜墙立面，或把中景元素拆分后按真实场景逐段布局。
- 中景设备接近现实可互动终端/宝箱/压力板的位置要做视觉避让，不让“背景假按钮”抢走真的机关识别度。
- 可以用 Godot 程序控制局部亮灯、检索灯脉冲及少量灯光明暗，而不是重新把全场编码成方框。

**显示大小**：原图约 200–350 像素宽/高，不可当成 320×240 活动屏下的最终像素尺寸；导入后应依据角色与原来 16×16 地板、32×32 角色图集选一个统一、可读的尺寸体系，再离线重采样生成游戏稿，避免场景里随意用不同小数倍缩放。这个包保留原始高分辨率，以免提前破坏细节。

**图集透明度**：源图为 RGBA。拆分文件沿用真实 alpha 并去掉极微弱背景边缘，仍需在 Godot 深紫背景上检查边缘毛刺及可能的鲜红/暖色杂点；必要时人工修边。

## 4. 一套安全的 Godot 视觉层级

从远到近：

1. `ARCHIVE_far` 远景背景 Sprite2D/分块纹理（建议 z=-30）
2. `ARCHIVE_mid` 中景柜墙/结构（建议 z=-20）
3. `ARCHIVE_props_back` 靠墙小物件（建议 z=-5）
4. 原有可交互机关、玩家、梯子、平台保持原来层级与碰撞
5. 少量 `ARCHIVE_props_front` 近景遮挡（建议 z=5，只有不影响玩家识别时才用）
6. 若需要屏幕扫描线、故障 CRT 效果，应在现有后处理/外部屏幕里实现，避免每个背景层重复叠加

这里的 z 值仅供规划：先检查现有节点的 `z_index`，再决定最终值，不能覆盖 UI、角色和视觉反馈。

### 关键技术约束

- `scripts/side_world.gd` 的 `texture_filter = CanvasItem.TEXTURE_FILTER_NEAREST` 应保留；背景和道具的导入过滤方式也必须检查。
- 320×240 是**屏幕输出分辨率**，不是整张大地图的宽高；镜头随玩家在 1024×640 世界里滚动。
- `world_backdrop.gd` 不能继续为 ARCHIVE 叠加原来一整片重复线框柜墙，否则画面会重叠脏乱。推荐只在 ARCHIVE 分支替换，其他五关行为保持不变。
- 请不要随手修改 `data/levels/archive_01.json` 中的箱石、WEIGHT 2 压力板、 `signal_archive_gate` 真实持续源信号、`archive_key` 宝箱、梯子、门、碰撞、出生点或区域回环。
- 背景没有碰撞；装饰型检索梯**不能冒充可爬梯**；摆件不要挡住传送出口、提示、角色或需要推动的箱石移动轨迹。
- 道具摆放必须稳定、可复现。允许根据固定种子变换部分静态摆件，但禁止每次载入随机堵塞路径或改变关卡认知。

## 5. 推荐工作顺序（先做小样再扩展）

1. **只接 ARCHIVE**：建资源目录、导入 12 张道具、添加远中景节点；保存改动列表，别触动其他关。
2. **先验收中层 320×240**：从 `ARCHIVE/main` 的进入区域截图，观察重压归档大厅是不是一眼像档案库，真正箱石与压板是否仍可读。
3. **上层和下层分别布置**：上层多检索桥及吊挂，底层多封存箱与破损 CRT，呈现明显的空间变化。
4. **检查视差/拼接**：沿 X/Y 全域移动镜头，确认无背景空洞、边缘接缝、悬空道具或穿模。
5. **制作和替换低分辨率游戏稿**：针对 320×240 画面确定每类对象的像素尺寸并清理 alpha 红边，保存原始大图可回退。
6. **保留截图和 QA**：附中层、上层、下层实机截图、真实机台屏幕截图与 320×240 源视口，说明是否仍有未完成的美术拆解。

## 6. 具体验收标准

- [ ] 玩家不看关名，能从抽屉柜墙/检索桥/文件推车辨认 ARCHIVE。
- [ ] 三层的背景有不同环境识别点，而不是同一条柜墙复制三次。
- [ ] 压板、箱石、梯子、真实宝箱、终端和出口不被假背景遮挡或误认。
- [ ] 320×240 原生屏面、横屏双指、键鼠和 3D CRT 外壳不受影响。
- [ ] 不会出现“画了楼梯但玩家走不上去”的误导性背景设施。
- [ ] 远/中景衔接、上下镜头、不同屏幕边缘都经过实际运行检查。
- [ ] ARCHIVE 的持续压力输入 `signal_archive_gate`、关卡解谜、回访、存档和宝箱都正常；其他五关无视觉回归。

## 7. 交付边界（实话）

这是一包**图像生成美术初稿与已拆分道具**，不是已经校验无缝、已锚点定位、已通过 Godot 的正式量产素材。缺少：远中景按 1024×640 地图的最终切块、实际碰撞对齐、逐像素接缝修正与动态灯效。不能把本包图片直接覆盖整张现有地图并宣布完成。
