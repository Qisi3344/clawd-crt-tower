## 0. 开发前先读：一句话讲清楚

**这是一款第三人称复古像素冒险游戏：在一个 360°、多层错落堆叠的复古 CRT 电脑阵列中，每台电脑的屏幕都是可玩的独立数字世界；玩家操纵像素螃蟹，始终在“屏幕画面内部”移动、解谜、战斗，并通过屏幕内部的节点切换到另一台电脑的屏幕世界。镜头始终追踪玩家当前所在的屏幕及屏幕中的螃蟹。**

**必须同时成立的两个核心创意：**

1. **电脑堆叠是整个游戏最重要的视觉空间。** 不是单独一台电脑，不是平面 UI 选关，不是只有一排电脑。立体电脑阵列有上下多层、前后左右与 360° 环绕关系，能从多角度看到不同的电脑屏幕，构成可识别、可记忆的整体结构。
2. **螃蟹从不出现在电脑实体外面。** 绝不在电脑机壳、键盘、电脑之间的空隙上爬行。螃蟹一直活在屏幕显示的游戏画面里。切换屏幕是**画面世界 A → 画面世界 B**，不是**爬出屏幕 → 穿越现实电脑堆 → 爬入屏幕**。

### 禁止再误解

| 错误实现（禁止） | 正确实现（必须） |
|---|---|
| 做一座实体电脑堆迷宫，让螃蟹爬外壳 | 电脑堆形成外层空间布局；螃蟹只在屏幕内的关卡活动 |
| 做成一个个毫无关联的全屏小游戏 | 每个屏幕世界属于同一个可见的多层 CRT 阵列，存在空间邻接与连接关系 |
| 把电脑阵列做成选关菜单后消失 | 电脑阵列贯穿游戏，进入关卡、观察周围和跨屏转移时一直是视觉母体 |
| 固定等距视角、镜头只盯着整座电脑塔 | **螃蟹所在屏幕内使用跟随主角的第三人称动态相机**；外层相机随目标屏幕转换位置 |
| 螃蟹从显示器玻璃里跳到现实 | 关卡内触发接口、传输点、故障裂缝；螃蟹直接在另一屏幕的内部场景出现 |
| 只放一张屏幕贴图或做假互动 | 每台可玩的屏幕必须有可操控、可碰撞、可推进的真实关卡状态 |
| 用廉价扁平 SVG/Flash 风拼个效果 | 用真实 3D 电脑低模 + 像素/体素美术 + 屏幕内可玩 3D/2.5D 场景 |

## 1. 美术总纲：必须贴近用户给的三张参考

### 1.1 风格定位

- **低多边形（low-poly）+ 体素/像素质感（voxel/pixel texture）+ 鲜明色块 + 90 年代 CRT 电子设备**。
- 电脑本体具有真实体积：厚厚的 CRT 显示器、方形机壳、软盘口、边框、键盘、旋钮、接线，呈现大块几何面和有意设计的像素纹理。
- 不做写实写旧办公桌、阴沉恐怖机房；不是写实 PBR 大型场景。参考图倾向**精致、怪趣、低模立体、配色大胆，局部发光**。
- 第一张参考的紫蓝与洋红屏幕、第二张的薄荷绿叠放电脑和不同绿色屏幕、第三张的简练高饱和游戏世界，作为共同风格锚点。
- **可读性比光效重要**：每个屏幕里都能一眼找到主角、可走区域、威胁、互动元素、出口。

### 1.2 色彩与材质

推荐基础色板（可微调，不做强制唯一值）：

| 用途 | 推荐色值/策略 |
|---|---|
| 深层空间 | `#16142B`、`#22223D` |
| 复古机壳 | `#C4C2AE`、`#8B9790`、`#75998F` |
| 电子蓝/青绿 | `#39B8CC`、`#52D5B1` |
| 梅紫/洋红 | `#8D62CA`、`#EF609D` |
| 危险警报 | `#F2C44A`、`#EB6870` |

**限制：** 不要整屏加同强度的霓虹 Bloom，不要过载赛博朋克粒子；不做灰糊水彩、劣质像素贴图、毫无体积的 Flash 平面风；不要随机混进写实高精度电脑导致画风断裂。

### 1.3 CRT 屏幕的表现

每台显示器需要：屏幕内凹感、玻璃反射的克制高光、极轻微的扫描线/抖动、微弱发光、屏幕角落轻微弧面失真。**所有效果不应妨碍玩家识别画面。** 游戏屏幕不是静态图片；可玩的内容要实时更新。

不同电脑型号、大小、倾角、屏幕主题要有变化，但风格统一。允许少量电脑损坏、倒置、悬挂、旋转，用于强化整体结构；不可让可玩屏幕因为角度彻底不可见。

### 1.4 像素螃蟹角色

- 低模/体素小螃蟹：圆润方块轮廓、明确两只螯和多对步足、可读的眼部特征。
- 动作至少包括：待机、左右/前后爬行、转身、跳跃、落地、挥螯攻击、受击、死亡/重生、互动。
- 必须真正有位移及碰撞，禁止用一个静态图标在背景上假移动。
- 横向爬行可以保留螃蟹独特的动势，但 W/A/S/D 的输入映射必须直觉；转向和移动不用完全符合现实生物学。
- 起步允许程序化低模，但**不能永久以几何立方体代替螃蟹**。

## 2. 空间与镜头：双层世界，一个玩家

### 2.1 外层：电脑阵列（World Shell）

这不是一个供玩家步行的物理关卡，而是一个始终存在的**3D 视觉空间、设备拓扑及镜头运动空间**。

- 初始布局参考：**12–18 台 CRT**，**3–4 层高度**，围绕中心以**360° 多方向错列**摆放，不限于平面环形墙。可用环形、螺旋、前后交叉、局部悬空结构组合。
- 要能从前方、侧方、上方看到多个显示器、部分机壳和连接线；禁止简单垒成毫无层次的矩形墙。
- 任意时刻有一个 `ActiveMonitor`；当前屏幕是玩家所处世界。邻近电脑作为外层背景与路线提示。
- 电脑之间有图结构（graph）：哪些屏幕可以相互切换，由真实关卡出口决定，不依靠玩家在机壳外移动。
- 首次开局用 2–4 秒以内的短镜头展示“层层叠叠的电脑宇宙”，然后镜头靠近当前活跃屏幕进入实际操作。

### 2.2 内层：单台屏幕世界（Screen World）

- 每台可玩 CRT 对应一个独立的 3D/2.5D 微关卡：有地形、移动、碰撞、敌人、交互对象、谜题、出口与保存状态。
- 游戏逻辑与坐标系发生在**当前屏幕世界内部**，而非 CRT 实体壳体世界。
- 不同屏幕可有不同地形拓扑、规则、视觉主题。主题不是只有颜色不同，玩法也不同。
- 屏幕世界之间通过 `ScreenLink` 有向或双向连接，支持任务门槛、钥匙、存档恢复。

### 2.3 双层镜头（非常重要）

1. **内部追随相机 `CrabFollowCamera`**：在当前屏幕关卡中持续追踪螃蟹，能按移动方向平滑平移/旋转；螃蟹占画面约中央偏下的位置，永远是辨识焦点。不要固定死等距相机。可采用略微俯视的第三人称跟随（具体角度按可玩性调整）。
2. **外部阵列相机 `ShellCamera`**：显示多层 CRT 布局，平时将当前活跃屏幕维持为主体，并让相邻的屏幕/电脑壳体在边缘适量露出；在跨屏时沿空间方向旋转、推移、重新对焦新的目标屏幕。
3. **两个镜头不能互相打架**：内部镜头负责玩家操控体验；外部镜头负责“我正在一整座 360° 电脑宇宙的哪块屏幕里”的空间连续性。不要用外部相机直接追踪一个在电脑壳体外虚构的螃蟹。
4. 在需要精细战斗的区域，可让**屏幕画面放大至占游戏窗口的大部分**，外层显示器边框及邻机保留一小部分。跨屏时再拉远露出堆叠阵列。
5. 对镜头遮挡必须做检测：如果前景电脑挡住了活跃屏幕，调整相机或临时降低前景遮挡物可见性；不能让螃蟹莫名消失。

**判定一条硬规则：螃蟹的唯一可控实体存在于 `ScreenWorld`，不得在 `WorldShell` 里创建第二只可操控螃蟹。**

### 2.4 屏幕切换的正确表现

示例：螃蟹在 `CRT_01` 的屏幕内来到右侧一个发光的“数据接口”，按互动键。

1. 屏幕内发生轻微像素错位/数据卷入；禁止显示螃蟹从玻璃里跳出来。
2. 输入短暂锁定并保存 `CRT_01` 的局部状态。
3. 外层镜头从 `CRT_01` 平滑环绕至电脑堆另一层的 `CRT_04`；能短暂看到堆叠结构与其他屏幕。
4. `CRT_04` 的屏幕从噪点切换为实时内容，螃蟹在它的 `entry_anchor` 内出现。
5. 内部跟随相机重新锁定螃蟹，恢复输入与战斗。

回退也同理。**这个过程是屏幕画面之间的空间转场，不是实体穿墙动画。** 目标转场以 0.7–1.4 秒作为初始调优范围，可按用户体验调整，且不要频繁黑屏加载。

## 3. 推荐技术栈与可行架构

**优先技术选择：Godot 4.x 稳定版 + GDScript + `.glb`/glTF 2.0 模型。** Blender 只作为必要时的低模调整工具。不强依赖外部付费工具。初期优先 PC（Windows）可玩版本；网页构建可在玩法稳定后评估性能与兼容性。

### 3.1 推荐渲染方案

Godot 的 `SubViewport` 可将独立 3D/2D 场景实时渲染成 `ViewportTexture`，并贴到外层 CRT 显示器屏幕材质上。它非常适合“多个屏幕中存在独立游戏世界”的设定。

**实现原则：**

- `WorldShell` 是 3D CRT 模型阵列。
- `ScreenWorld` 是屏幕对应的小型 3D 场景，拥有自己的物理、螃蟹位置、Camera3D 与交互系统。
- CRT 的显示区域材质使用对应 `SubViewport` 画面作为贴图；关闭屏幕用休眠贴图/截图代替。
- 所有输入只传给 `ActiveMonitor` 对应的 `ScreenWorld`；非活动屏幕不接受玩家输入。
- `ScreenTransitionManager` 保证跨屏时只激活一个玩家控制权，不重复触发传送，不丢存档。
- 若 SubViewport 多场景并存太吃 GPU，可改为**一个高质量活跃世界 + 邻近 1–2 台低分辨率预览 + 其他屏幕缓存帧/休眠动画**；外层电脑堆仍保持可见。

### 3.2 参考场景树

```text
GameRoot
├── WorldShell [Node3D]
│   ├── ComputerArray [Node3D]
│   │   ├── Monitor_00 [MonitorInstance]
│   │   ├── Monitor_01 [MonitorInstance]
│   │   └── ...
│   ├── ShellCameraRig [Node3D]
│   │   └── ShellCamera [Camera3D]
│   └── AmbientPropsAndLights
├── ScreenWorldManager [Node]
│   ├── ActiveScreenWorld [instanced playable scene]
│   ├── ActiveSubViewport [SubViewport]
│   └── CachedNeighborScreens
├── ScreenTransitionManager [Node]
├── ProgressionAndSave [Node]
├── AudioManager [Node]
└── HUD [CanvasLayer]
```

### 3.3 模块划分

| 模块 | 职责 |
|---|---|
| `ComputerArrayBuilder` | 根据配置生成 360° 多层错落 CRT 排列，可手动调整布局和邻接关系 |
| `MonitorInstance` | 屏幕网格、玻璃材质、屏幕 ID、纹理输入、状态指示灯、镜头锚点 |
| `ScreenWorldManager` | 加载/卸载/休眠微关卡，维持唯一活跃螃蟹 |
| `CrabController` | 内部场景的真实移动、碰撞、跳跃、攻击、受击 |
| `CrabFollowCamera` | 当前屏幕世界内部第三人称跟随、碰撞避免、镜头缓动 |
| `ShellCameraDirector` | 根据活跃 CRT 位置调整外层镜头；转场时经过空间旋转与聚焦 |
| `ScreenLinkGraph` | 电脑画面之间的出口/入口、锁条件、可达性检查 |
| `ScreenTransitionManager` | 输入冻结、效果播放、位置映射、回退、错误恢复 |
| `PuzzleSystem` / `CombatSystem` | 可复用谜题机制与敌人机制 |
| `SaveSystem` | 当前屏幕 ID、关卡进度、道具、机关与敌人状态 |

### 3.4 屏幕连接数据示例

```json
{
  "link_id": "link_01_to_04",
  "from_screen": "CRT_01",
  "from_exit": "data_port_right",
  "to_screen": "CRT_04",
  "to_entry": "signal_entry_left",
  "required_flag": "has_signal_key",
  "transition_type": "pixel_glitch",
  "bidirectional": false
}
```

所有屏幕 ID、位置、屏幕世界资源路径、出入口和条件从数据配置读取。**不要在跳转代码里写死“从 A 只能去 B”。**

## 4. 第一版关卡设计：六个相互连通的屏幕世界

先开发**六台有实际内容的可玩电脑**，放进**至少 12 台 CRT 构成的三层 360° 阵列**。其余电脑可显示独特待机画面或作为后续拓展位置，但不能全部显示同一张贴图。

| ID / 名称 | 屏幕世界画面 | 实际玩法 | 出口与进度 |
|---|---|---|---|
| `CRT_00` BOOT / 启动区 | 青绿色像素网格、旧式终端、巨型光标 | 15–30 秒可交互移动教程，熟悉攻击与扫描 | 通往 `CRT_01`、`CRT_02` |
| `CRT_01` ARCHIVE / 丢失档案 | 紫蓝文件柜、像素窗格、被撕裂的图标 | 抽屉与文件线索拼合谜题 | 解锁“信号钥匙”，通 `CRT_03` |
| `CRT_02` ERROR / 故障区 | 红蓝错误块、错位台阶、扫描线陷阱 | 移动平台、节奏躲避与基础病毒敌人 | 通往 `CRT_04` |
| `CRT_03` CIRCUIT / 接线区 | 荧光绿数据线、节点、环形电路 | 转接线路，让能量到达指定接口 | 解锁中央核心的门禁 |
| `CRT_04` TRASH / 回收站 | 黄色碎纸文件、回收站残片与悬浮数据 | 双阶段病毒战 + 搜索隐藏记录 | 获得剧情碎片，通 `CRT_05` |
| `CRT_05` CORE / 主控屏 | 黑紫核心、巨型坏点、反向滚动日志 | 整合已获取线索完成综合谜题，打最终原型战 | 第一章结局，提示下一层电脑阵列 |

各屏幕**视觉语言与互动规则必须有辨识度**。不得仅修改背景颜色，然后重复同一个走迷宫玩法。至少存在一条需要回访旧屏幕才能推进的新路线。

### 4.1 主循环

`探索画面 → 操控螃蟹发现线索/危险 → 解谜或战斗 → 获得权限/道具 → 找到屏幕内连接点 → 转移到另一台 CRT 的画面 → 发现新的秘密 → 回访旧屏幕。`

### 4.2 最小战斗系统

- 基础移动、跳跃、螯击、闪避；攻击有明确打击反馈和短暂硬直。
- 至少 2 类敌人：`PopupBug`（追踪/弹跳）与 `GlitchCrawler`（定时突进）；每种都有明显预警、攻击与受击动画。
- 初始玩家生命 3 点，受击短暂无敌帧；支持死亡后在当前屏幕入口重生，不清空整个世界。
- 基础 BOSS 只要求有清楚的攻击节奏、2 段行为变化；不要先做复杂特效却没有可玩的战斗反馈。

### 4.3 解谜系统

至少 3 种真正逻辑不同的谜题：

1. **文件复原**：搜寻多块碎片，依据图案/文字/顺序还原文件，取得新权限。
2. **信号连线**：旋转节点连接线路，输入端流向输出端才触发机关。
3. **故障时序**：利用闪烁/断连规律穿越陷阱或让特定设备处于正确状态。

谜题状态必须能保存；失败可以重试；不能以全随机暗箱代替玩家可理解的规则。

## 5. 操作与 UI 约定

首版 PC 键鼠：

| 输入 | 行为 |
|---|---|
| W / A / S / D | 螃蟹在**当前屏幕世界内部**移动，方向相对内部相机/关卡逻辑 |
| 鼠标移动 | 适度环绕或辅助旋转内部视角（保证不晕）；可在设置中关闭 |
| Space | 跳跃 |
| 鼠标左键 / J | 螯击 |
| Shift | 闪避或加速短冲 |
| E | 交互、调查、进入**屏幕内传输节点** |
| Tab | 显示“电脑阵列节点图”（指明当前电脑和已发现连接） |
| Esc | 暂停、设置、返回菜单 |

UI 必须简洁，有“旧电脑系统但现代游戏易读”的质感；不要把整屏覆盖成现代手机 App 或复杂窗口堆。交互对象需要高亮、声音和短文字提示，但不要对每个物体盖一大块文字面板。

### 6.3 资源处理规范

- 优先 `.glb` / `.gltf` 2.0；FBX/OBJ 资源必要时用 Blender 转换。
- 统一世界单位、缩放、朝向、命名、材质通道；每台 CRT 必须有独立的可替换 `ScreenMesh`/`ScreenMaterial`，可运行实时画面。
- 静态外壳可做 instance/重复网格；对远处电脑做低细节与渲染缓存。
- 保留模型作者署名及原始许可记录，不把第三方模型错误写成“全部原创”。

## 7. 性能策略（否则 360° 多屏幕会成为 GPU 黑洞）

- **禁止对全部 12–18 台 CRT 同时高分辨率渲染独立动态 3D 关卡。**
- 当前活跃屏幕示例为 `320×240` 或 `480×360` 内部渲染分辨率（CRT 默认 4:3），按清晰度/性能调优。其他电脑显示低分辨率预览、循环待机动画或缓存帧。
- 屏幕世界使用资源池、按需激活、离开后保存并休眠；后台不跑全部 AI 物理、寻路及粒子。
- 电脑外壳重用网格与材料；屏幕玻璃的 Bloom、噪点和扫描线统一低开销 shader。
- 不依赖云端请求才能玩；目标机器为普通桌面 PC，稳定性优先于镜头炫技。
- 从第一阶段就加入 FPS、draw calls、活动 SubViewport 个数、内存占用等调试面板。

## 9. 开发顺序：先证明概念，再增加内容

### P0 — 美术与技术原型（第一优先级）

**交付：** 4 台真实 3D 复古 CRT 组成简单立体堆叠、至少 2 个可互相切换的可玩屏幕、1 只可操控像素螃蟹、双层摄像机。

验收：屏幕显示的不是视频或静态贴图，而是真正能操控的关卡；至少一次 A → B 跨屏跳转成功；主角绝不在屏幕外；内部相机跟随正常；外部能看见真实立体电脑外壳和相邻屏幕。视觉轮廓达到参考图基本水准。

### P1 — 360° 多层电脑阵列（核心卖点）

**交付：** 3 层以上、12 台以上的 CRT 阵列，360° 错落排列；可观察到至少 3 种机型/轮廓；双层镜头能够可靠转向不同方位与高度的目标屏幕。

验收：不是单面墙、不是排成一排、不用固定斜 45° 的假 3D；顶部/侧面/后方都存在电脑，镜头有空间运动与遮挡处理。

### P2 — 跨屏架构（第二核心卖点）

**交付：** 六个 `ScreenWorld` ID、有各自坐标、一个真实可操作的屏幕间跳转系统、图结构和状态保存。

验收：螃蟹从 A 屏幕内部传到 B 屏幕内部，外部镜头随阵列目标切换；任何时刻不会出现屏幕外的螃蟹。连接信息不硬编码。

### P3 — 完整垂直切片

**交付：** 六个有辨识度的屏幕关卡；至少 3 种谜题、2 种怪物、1 个阶段型 Boss、可回访路线、进度保存、第一章结尾。

验收：能从开局玩到结尾；不是纯观赏 3D 模型，不是按 E 连续看切屏动画，不是单一小游戏复制六份。

### P4 — 艺术打磨、优化和发布

**交付：** 螃蟹动画、屏幕切换反馈、音效、像素化后处理、镜头与操作调优、性能分析、错误恢复、打包构建。

验收：普通 PC 操作清楚、无明显穿模、跨屏不死锁、存档不丢失、画面不因效应过载而读不清。

## 10. 不可妥协的验收清单

开发代理每次提交都要核对：

- [ ] 从游戏内能真实看到**360°、至少三层高、多机型**的 CRT 电脑堆叠，而不只是一个背景截图。
- [ ] 玩家只有一只可控制螃蟹，**始终只存在于某个屏幕画面内部**。
- [ ] 螃蟹移动时内部游戏镜头追踪主体，画面不是固定死的俯视等距视角。
- [ ] 屏幕 A 到 B 的传送没有“螃蟹实体爬出 CRT 机壳”的错误动作。
- [ ] 外层相机能够转向上下层和身后电脑；目标屏幕不被其他外壳完全遮死。
- [ ] CRT 屏幕实时显示各自的小型游戏世界，不是一排纯贴图/一段循环视频。
- [ ] 至少一个屏幕内有真的解谜逻辑，另一个有真正战斗/碰撞反馈。
- [ ] 重新访问已完成关卡时状态连贯；关闭并重开游戏也可恢复进度。
- [ ] 低模像素/体素 + 丰富色彩的风格统一，无廉价 Flash/SVG 平面假 3D。
- [ ] 所有第三方模型可追踪下载来源、作者和许可，必要署名已写入文档。
- [ ] 项目可以从源码按 README 启动，不依赖开发者本机的绝对路径。

**不接受的“完成”说法：** 只有设计概念图；只有单 HTML 页面和一张背景图；只有会旋转的电脑模型；只有一只螃蟹能在电脑壳外移动；只有几个空关卡传送门；只有视频/GIF 冒充可玩功能；声称完成却没有实际运行与截图证明。

## 12. Codex / 开发 Agent 的执行规则

1. **先读本手册与参考图，输出 1 页结构化实施计划，然后直接开始建可运行项目。** 不许将核心概念改成自己熟悉的普通走迷宫游戏。
2. 优先完成 P0 + P1 的可运行视觉/技术证明，**确认真实 3D 电脑堆叠、屏幕内螃蟹和镜头**。这三个不对，后续谜题与敌人做得再多也算方向错误。
3. 每一阶段要提供：可运行入口、实装文件清单、功能演示截图/录屏（条件允许）、已实际测试项、尚未完成项、下一阶段优先工作。
4. 可使用合法低模开源/开放许可资源，但下载前检查授权；遇到需要账号的下载需等待用户提供合法可用文件，不可绕过。
5. 如果缺模型，先做**有设计感、有体积的临时 CRT 低模**保证机制可运行，然后替换；不要拿灰色盒子堆当最终美术。
6. 重大技术妥协必须写清楚。例如实装为 2.5D 时，应说明如何保证屏幕内真实可玩、外层 3D 空间连续，而不是悄悄删掉 360° 和第三人称跟随。
7. 不宣称虚假的完成度。没有做的标记 `TODO` 并说明阻碍；不要用占位画面、伪按钮、硬编码剧本糊弄验收。
8. 最终的“首个可玩版本”应可以被用户**真正操控和探索**，而不是只看漂亮的电脑阵列旋转。

### 开发第一条命令式任务

> **构建 P0 可运行工程：** 把四台立体低模 CRT 摆成上下错层，至少其中一块 CRT 使用实时 SubViewport 展示可玩微场景；创建一只动画化像素螃蟹，WASD 真正移动、镜头第三人称跟随；显示屏幕边框、邻近电脑及立体深度；然后制作 A → B 的跨屏小演示。**所有时刻，螃蟹只能在屏幕显示的世界里。** 如果屏幕内实现失败，优先解决渲染与操作架构，禁止转而把螃蟹放到电脑壳体外面取巧。
